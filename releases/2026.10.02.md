# Uptimy Agent for Kubernetes: label it and it's monitored

Yesterday we released [Uptimy Agent](https://github.com/uptimy/agent), an open-source uptime monitor that runs inside your cluster. Today it gets the part that makes it worth running there: you don't create monitors anymore. You label what you want watched, and the agent works out how to check it.

```bash
helm install uptimy-agent oci://ghcr.io/uptimy/charts/uptimy-agent -n monitoring --create-namespace
kubectl -n shop label service checkout upti.my/monitor=true
```

Within 30 seconds `shop/checkout` is monitored, and it alerts wherever your alert channels point.

## Label a resource, get the right check

| You label | The agent checks |
|---|---|
| A Service | An HTTP request to `checkout.shop.svc` on the pods' own readinessProbe path (`/healthz`, `/ready`), or a TCP connect for ports that aren't HTTP |
| An Ingress or HTTPRoute | Each of its hostnames, over HTTPS when the Ingress has TLS for it |
| A Deployment, StatefulSet or DaemonSet | That all its replicas are ready |
| A CronJob | Every run, read from its Jobs (see below) |

Put the label in your manifests or Helm chart and every new app, in every environment, is monitored the moment it's deployed. Remove the label or delete the app and its monitor goes away. Annotations adjust the check: `upti.my/name`, `upti.my/path`, `upti.my/interval`, and [a few more](https://github.com/uptimy/agent#auto-discovery).

A Service can also reuse Kubernetes' own health instead of a request of its own: with `upti.my/type: kubernetes` it's up while it has a ready endpoint, so the app gets no extra traffic. That works for any port and protocol, databases and gRPC included.

## CronJobs without a curl at the end

Monitoring a cron job usually means editing it to ping a URL when it's done. A labeled CronJob needs nothing: the agent follows its schedule and time zone and reads each run from the Job Kubernetes created:

- when it started and how long it took
- whether it completed or failed, and why: `Job backup-2984 failed: BackoffLimitExceeded; container backup exited with code 137 (OOMKilled)`
- a run that didn't happen, or didn't finish in time, alerts as missed

Suspend the CronJob and its heartbeat pauses with it.

## See what's in the cluster

**Settings → Kubernetes** lists the cluster's Services, Ingresses, workloads and CronJobs, which ones are monitored, and the `kubectl label` command for any of them, or for everything on screen at once. It also shows what the last scan couldn't use, like a mistyped label value or an invalid annotation, so a resource that doesn't show up tells you why. The agent stays read-only: it never changes your cluster.

## Get started

```bash
helm install uptimy-agent oci://ghcr.io/uptimy/charts/uptimy-agent -n monitoring --create-namespace
kubectl -n monitoring port-forward svc/uptimy-agent 8080:80
```

Sign in as `admin` with the password from `kubectl -n monitoring logs deploy/uptimy-agent`, add an alert channel, and label something. Not on Kubernetes? The agent also runs on [Docker](https://github.com/uptimy/agent#docker) and [Railway](https://railway.com/deploy/uptimy-agent?referralCode=-G2iM8&utm_medium=integration&utm_source=template&utm_campaign=agent-k8s-release).

And when the whole cluster goes down, nothing inside it can tell you. **Connect to Uptimy** in the agent's settings and [Uptimy](https://www.upti.my/?utm_source=github&utm_medium=release&utm_campaign=agent-kubernetes) alerts you from outside when the agent stops checking in.
